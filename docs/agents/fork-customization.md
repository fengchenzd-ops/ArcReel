# 在定制分支上开发

`codex/personal` 是长期分支，放我们自己的定制，同时定期合并开源上游的最新代码。定制代码怎么写，决定了以后每次合并的成本。本文只存在于定制分支。

## 分支与同步

- `upstream` 是开源原仓库，`origin` 是我们的 fork。`main` 只做 `upstream/main` 的镜像，不提交定制。
- 同步步骤：拉取 `upstream/main` 并快进本地 `main`，把 `main` 合并（merge）进 `codex/personal`，再推送到 `origin`。定制分支已推送且长期存在，用 merge 保留历史。`CONTRIBUTING.md` 里「分支不超过 3 天、rebase 主线」的约定针对提给上游的 PR 分支，不适用于定制分支。
- 合并后运行 `uv run python scripts/gate.py --changed`。同步后 `origin/main` 与上游一致，`--changed` 选中的正好是定制改动涉及的域，用来发现上游改动是否破坏了定制。
- 想贡献给上游的改动从 `main` 拉分支，PR 里只含这一项改动，不带定制。

## 写定制代码

核心做法是把定制放进新文件，在上游文件里只留**接入点**：一行 import、一次注册或一次调用，逻辑都在新文件里。新文件不会和上游冲突，接入点越少、越短，合并越省事。

- **新文件优先**：新模块、新路由文件、新组件、新测试文件。新路由在 `server/app.py` 里加一行 `include_router`，就是一个接入点。
- **走现有扩展点**：`agent_runtime_profile/.claude/` 下新增 skill 或 agent；前端文案放进新的 i18n 命名空间（见下文）。
- **接入点旁加一行注释**，以 `fork:` 开头，写明对应哪项定制，合并冲突时可以一眼认出哪部分是我们的。
- **上游文件只改接入点本身**：保持周围代码原样，包括顺序、命名和格式；上游代码的问题另提给上游，或单独记为一项定制。
- **改变上游已有行为**（改默认值、改逻辑）时，优先加配置项或参数开关，保持上游默认路径不变；做不到时把改动压到最小，并在登记表写清意图。
- **锁文件和生成文件**由工具写入。`uv.lock`、`pnpm-lock.yaml` 冲突时先取上游版本，再用 `uv add`、`pnpm add` 重新加入定制依赖。定制依赖越少越好。
- **每项定制行为都配测试**，放在新的测试文件里。合并后上游改动破坏定制时，靠这些测试发现。

### 编号类资源

以下资源按编号线性排列，定制分支各自编号会和上游撞车，冲突后果最重：

- **数据库迁移（`alembic/versions/`）**：迁移是单链，应用启动时执行 `upgrade head`。定制分支新增迁移后，上游再新增迁移，合并后会出现两个 head，启动失败。优先避免改数据库结构；确实需要时，每次合并后运行 `uv run alembic heads`，出现多个 head 就用 `uv run alembic merge heads` 生成合并迁移并提交。
- **项目 schema 迁移（`lib/project/project_migrations/`）**：版本号写进每个项目的 `project.json`，定制步骤会占用上游的下一个版本号，合并后同一版本号含义不同，已迁移的项目无法再按上游步骤升级。需要改项目数据结构时，先找用户确定方案。
- **前端 i18n**：定制文案放进新的命名空间文件，`frontend/src/i18n/` 下 `zh`、`en`、`vi`、`ru` 四种语言各一份，再在 `frontend/src/i18n/index.ts` 的 `I18N_NAMESPACES` 里登记一行。往上游命名空间文件里加键，上游每次改同一文件都可能冲突。

## 合并冲突

- **冲突发生在上游文件**：以上游的新代码为基础，按登记表里的意图重新接入定制，不整段保留我们的旧版本。
- **上游已经实现了同等功能**：报告用户，建议删除定制、改用上游实现，确认后更新登记表。
- **无法按意图判断怎么合**：停下来找用户，说明冲突位置、双方改动和可选方案。
